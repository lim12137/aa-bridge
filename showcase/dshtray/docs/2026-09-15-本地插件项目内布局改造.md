# DshTray 安装器「本地插件完全项目内」默认布局改造（v2.0.4 实装记录）

> 原方案由用户起草（参考机存量改造 + 安装器默认布局设计）。本文档记录 v2.0.4
> 实装时的三处实测修正——原方案的三个假设在干净机器上不成立。

## 原方案保留的部分
- 载荷：两个本地插件（dsh-web-search-openai、dsh-llm-extra-retry）随安装器
  分发到 `app\home\.dsh\local-plugins\`（按各自 package.json files 字段裁剪）。
- 解析锚点 junction：`app\node_modules → app\home\.dsh\profiles\node_modules`，
  由托盘在拉起 dsh 前幂等确保（ensureModuleAnchor）。junction 悬空无害：
  目标森林由 dsh 首启生成。
- NSIS 侧不建 junction、不预写 profiles\web\package.json（原方案结论正确）。

## 实测修正一：约定目录不会自动登记
原方案假设「首次启动 dsh 后 profiles\web\package.json 会自动生成 link: 行」。
干净 home 实测：仅把插件放入 .dsh\local-plugins，dsh 首启既不生成 link 行、
也不注册插件。参考机上存在该行是当初手工安装写入的。
**实装**：托盘内嵌挂载器 `app\wire-plugins.mjs`（node 跑，幂等），dsh 首启
生成 profile 后把每个随装插件写入 dependencies（link: 绝对路径）与
dsh.profile.bundles，再 `dsh plugin --profile web install`（=pnpm install，
实测 dsh 启动自身也会物化 link 依赖，pnpm 仅确认，257ms）。

## 实测修正二：重启装载不能在同一 worker 线程内续跑
worker 线程内「挂载→物化→杀 dsh→再拉起」的长链路会静默挂起；另经面包屑
定位：**worker 线程内 process.popen().readAll() 读 cmd 子进程会永久阻塞**
（taskkill 直连子进程不受影响）。铁律：worker 里子进程一律 process() 异步
发射，靠文件变更/完成标记轮询进度。
**实装**：挂载轮完成后经 thread 共享区（dshTray.reopen）请求主线程定时器
重新派发一次 openWeb——全新 worker 完成重启装载，本轮不开壳。

## 实测修正三：原方案伪代码路径双写
原方案 `appPath + "\app\home\..."` 多了一层 app\。实装以 cfg.appDir /
cfg.homeDir 分别传入，锚点为 `cfg.appDir\node_modules → cfg.homeDir\.dsh\profiles\node_modules`。

## v2.0.4 新机器默认流程
安装（载荷含 local-plugins + wire-plugins.mjs）→ 托盘启动 → 拉起 dsh 前确保
锚点 junction → dsh 首启生成 profile → 挂载器写 link+bundles → pnpm 确认 →
自动重启 dsh → 插件注册（日志出现 `[dsh-web-search-openai] v0.6.2 registered`）
→ 打开网页。全程 C 盘用户目录零写入（HOME 重定向在 app\home）。

## 已知技术债（沿原方案）
- dsh-settings shim：仅参考机手动改造时需要；随装插件当前版本（0.6.2/0.1.0）
  已不使用 rc.2 settings API，新机器无需 shim。上游发布带
  installSettingsSection/settingsNamespace 的核心后，该债自动消失。
- 存量机迁移残留：若 profiles\web\package.json 仍链 C 盘旧路径，改为项目内
  绝对路径即可；.pnpm-workspace-state.json 如锚在旧路径需同步修正。
